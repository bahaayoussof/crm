- [2026-09-02] **SMS timeout → `PROVIDER_UNREACHABLE` — FIXED (same branch `fix/outbound-reply-resilience`, ADR-052 follow-up, buglog bug-180).** `integrations/sms/textbee.provider.ts`: the `try/catch` around the `fetch(...)` call (and only that call) IS the structured "no HTTP response was received" seam — everything after it (`!response.ok`, `data.success === false`, `failureCount > 0`) is a provider that responded and rejected. Previously the catch was a bare `catch {}` that rethrew `AppError(502,"SMS_DELIVERY_FAILED")` for both, so an `AbortSignal.timeout(20_000)` firing was misreported as `PROVIDER_REJECTED`. Now the catch throws `AppError(504,"SMS_DELIVERY_UNREACHABLE")` — `const timedOut = error instanceof DOMException && error.name === "TimeoutError"` only picks the message string; both timeout and a raw `TypeError: fetch failed` (DNS/socket) go to the same code. `outbound-delivery.ts` `REASON_BY_ERROR_CODE` gained `SMS_DELIVERY_UNREACHABLE: "PROVIDER_UNREACHABLE"`. `sms.service.ts` was NOT touched (`deliverOutboundSmsReply` already funnels every provider throw through `outboundFailureReason`). Test seam: mock `fetch` via `vi.stubGlobal("fetch", vi.fn().mockRejectedValue(new DOMException("...", "TimeoutError")))` — no fake timers, no real wait. `AbortSignal.timeout()` on abort rejects `fetch` with a `DOMException` named `"TimeoutError"` (Node 20+ undici).
